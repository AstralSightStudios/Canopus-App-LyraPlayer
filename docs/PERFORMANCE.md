# 界面性能与传输速度

下面的数字都来自 Mirage（QEMU 模拟的 BEST1503），不是真机。模拟器的 CPU、显示管线和蓝牙链路都与真机不同：
CPU 数字只能说明相对关系，传输数字只能说明协议结构，真机的帧率、字形缓存首次绘制、渐变加透明度的混合开销
都没有验证。

## 界面

计时用模块里的临时探针（固件毫秒时钟，已移除）加 NSH `ps` 的 Idle 占比（`scripts/mirage_perf.py`）。

| 项目 | Band 10 Pro `.043` | Band 11 `.155` |
|---|---|---|
| 曲库页创建 | 8 ms | 5 ms |
| 播放页创建 | 26–29 ms | 24 ms |
| 刷新 tick（每 100 ms）平均 | 0.7–1.4 ms（含歌词建行的 tick） | 约 0.8 ms |
| 歌词高亮 / 滚动目标更新 | ≤ 2 ms | ≤ 1 ms |
| 静止时 CPU | Idle 94–96 % | — |
| 手指拖动歌词列表 | Idle 约 75 % | — |
| 对照：拖动系统启动器 | Idle 约 75 % | — |

* 拖动歌词与拖动系统启动器的 CPU 占用相同；把非当前行缩到 7/8（`TRANSFORM_SCALE`）开关对占用没有影响
  （75.0 % 对 74.9 % idle），所以保留缩放。Mirage 里拖动本身的开销主要在显示与触摸管线。
* Umem 堆在打开应用前后的变化在 ±100 KiB 内，测不出模块界面自己的占用（模块常驻部分约 154 KB 另计）。

### 最坏的一次 tick

界面全在刷新定时器所在的 UI 线程上，一次 tick 做得太久，触摸、滚动动画、进度条都会跟着停。
原来有两处会一次做太多：

* 曲库页一次把最多 64 行全建出来：40 首的曲库一次 tick 105 ms；
* 歌词每 tick 固定建 6 行，播放页可见时也一样：一次 tick 最长 87–91 ms（每行约 15 ms，主要是字形度量）。

现在按时间预算建对象（`lv::Budget`，用固件毫秒时钟，每次至少建一个）：

| 位置 | 预算 | 最坏 tick（043） |
|---|---|---|
| 曲库行 | 24 ms / tick，自上而下，没建完下个 tick 继续 | 105 ms → 37 ms |
| 歌词行，播放页在前台 | 16 ms / tick | 预算加一行，约 30 ms（未单独测） |
| 歌词行，歌词页在前台 | 56 ms / tick | 91 ms → 57 ms |

代价是曲库行和歌词行是逐步出现的：首屏的几行在第一、二个 tick 内就位，其余在之后几百毫秒到几秒内补齐。
真机上每行的成本大概更高，预算按时间而不是按行数，所以会自动少建几行。

### 曲库改版（2026-10-23）

曲库改成封面缩略图列表、底部迷你播放条、当前行律动条之后重测。同一台 `.043`，12 首示例曲（`seed_library.py`），
每个场景前冷启动一次，`mirage_perf.py 043 library|launcher|lyrics`（4 s 慢拖，与上表同一方法）：

| 场景 | 静止 Idle | 拖动 Idle |
|---|---|---|
| 曲库（播放中：迷你播放条、律动条 5 Hz） | 92.1 % | 77.8 % |
| 对照：系统启动器 | 96.2 % | 82.6 % |
| 歌词页 | 95.7 % | 73.9 % |

* 曲库页唯一的常驻重绘是律动条。同一构建里对比播放与暂停（暂停时律动条静止）：10 Hz 时 87.9 % 对 95.6 %，
  把律动条冻住后播放中也是 96.8 %，所以这 8 个百分点全来自它。两种猜测都试过、都没有改善：
  律动条固定尺寸、改用渐变断点表示高度（不触发列表重新布局）是 88.8 %，而且这么窄的对象上固件没有画出断点；
  把当前曲目的缩略图读进内存、不再每次从 flash 读文件是 88.1 %。也就是说这块固件上每次覆盖封面的重绘本身就贵，
  与面积和图片来源关系不大。最后把律动条降到 5 Hz（每两个 tick 一步）：91.9 %。
* 列表缩略图由手表从 `cover.bin` 生成，每个 tick 最多一张、每首歌只生成一次（读一遍 124 KB 的封面）；
  12 首的曲库第一次打开时，缩略图在一两秒内补齐。
* 播放页封面加了投影。固件每次重绘投影都从头计算模糊，而 LVGL 会重绘“延伸绘制区”（投影向外的范围）与脏区相交的对象：
  标题跑马灯的框原本伸进投影下沿 13 px，长标题的歌（`夜もすがら君想ふ (10th Anniv.)`）在播放页静止时只有 53 % Idle。
  现在投影收紧（宽 36、下沉 10、spread −10，向下延伸 19 px），标题框从投影范围之下开始（`layout.rs` 有测试守着）：
  同一首歌 63 %，再把投影整个关掉也是 63 %，说明投影已经不参与；剩下的是标题跑马灯本身的持续重绘（标题的跑马灯代码没改，改版前的构建没有在这首歌上单独测过）。
  标题放得下的歌，打开播放页十几秒后 Idle 约 90 %（歌词按预算逐行建对象的那段时间更低，见上）。
* 换行、切歌的动画由一个 16 ms 的 LVGL 定时器驱动，只在有东西在动时存在（一次换行约 0.6 s、一次切歌约 0.5 s），
  动完即删；静止时的数字与上表相同。

## 传输速度

2026-10-23 使用 AstroBox Core `main`（`713ef76`）重新测量。旧版“已经达到链路下限、无法再优化”的结论撤回：
此前 `smoke --stdin` 逐条等待响应，`--pipeline` 只改变主机队列深度，并不是真正的并发传输；旧驱动还会把初始化的
`status` / `connect` 返回误当成后续请求的结果。现在连接完成后才发 `ready`，驱动从该标记之后匹配结果，并检查模块状态码。

### 实测与优化

同一组文件：MP3 401,283 B、176×176 ARGB8888 封面 123,916 B、LRC 295 B，合计 **525,494 B**、1,139 帧。
以下计时从发送 BEGIN 到 COMMIT 确认并收齐发送结果，不包含连接认证、构建、重启或文件回读。

| 设备 | 原有 10 ms 响应轮询 | 自适应轮询＋重复导入修复 | 吞吐变化 |
|---|---|---|---|
| Band 10 Pro `.043` | 43.8 s，11.7 KiB/s | 35.0 / 34.6 s，14.7–14.8 KiB/s | 约 +25–27% |
| Band 11 `.155` | 44.8 s，11.5 KiB/s | 34.0 / 33.7 s，15.1–15.2 KiB/s | 约 +32% |

Band 11 的优化后测试使用新建模拟设备，因为旧设备的表盘存储区已满；它不是同一设备实例的严格 A/B。
所有列出的传输都没有续传。最终成功还需要下述回读与界面验证，不能只看导入 ACK。

Core 自带传输 profiler 显示，原路径发送间隔中位数约 38 ms，`send_batch_spp` 耗时低于其 1 ms 计时精度，
没有 NAK、重传或 500 ms ACK 停顿。因此没有更改 SAR 的 ACK、顺序锁、发送窗口或重试机制。

优化在 Canopus Supervisor 的蓝牙 owner 定时器：收到请求后改用 2 ms；请求、响应和事件队列清空后恢复 10 ms。
UI owner 和后台音频轮询保持 10 ms，所有定时器操作仍在各自的 owner 线程上。固定 2 ms 的实验能达到 15.5 KiB/s，
但没有保留其常驻高频唤醒。`.043` 熄屏空闲 Idle 从基线平均 96.7% 到自适应平均 96.9%，这只是模拟器采样，不能证明真机续航不变。

CPC2 仍逐条确认；Connect 数据上限仍为 480 B，DATA 净荷 464 B。进一步扩大包或并发窗口需要独立的协议、队列和真机验证，
不能从这些结果推导“帧大几倍就快几倍”。插件选择较低音质仍可以减少需要传输的音频字节。

### 多帧在途（2026-10-24）

真机上用户实测导入从没超过 10 KiB/s。CanopusConnect 走的是原始二进制（`Payload::Binary`），没有 Base64 或 JSON 转码，
所以这不是编码开销；慢在结构上：

* 每帧一问一答，下一帧要等上一帧的应答回来。真实蓝牙链路上一次往返要几个连接间隔，一次只有一帧在途，
  速度就是“每个往返一帧”，与模拟器的 15 KiB/s 无关；
* AstroBox 每台设备同时只允许一条 Connect 消息在途（旧的 `connect_lock`）；
* 插件宿主每发一帧都要绕前端做一次权限检查；
* 固件的拥有者线程每 10 ms 只处理一个排队的请求。

AES 不是瓶颈：每帧 464 字节，加解密相对一次往返可以忽略，所以没有做“不加密的大文件通道”。

改动（插件、AstroBox core、固件三处）：

| 位置 | 改动 |
|---|---|
| Lyra 插件 `import.rs` | 发送流水线化，最多 3 帧在途（`IN_FLIGHT`） |
| AstroBox core `canopus/connect.rs`（在上游的 `ConnectWindowSender` 之上） | 插件的 `canopusconnect.send` 不再被 `connect_lock` 串成一次一条，而是有自己的 3 条在途窗口（`MAX_CONNECT_PLUGIN_SLOTS`），与 CRPack 的数据窗口分开，互不饿死；入队沿用上游的有序写入锁，并发的发送仍按调用顺序进入 SAR；每条占一个设备 RPC 槽直到设备应答，4 槽队列不会溢出，始终留一槽给 Manager |
| AstroBox core `canopus.rs`、`package.rs` | CPC2 头和模块包的 ABI 主版本跟框架一起升到 2.0（Supervisor 对主版本不符的请求不回应，旧值会让所有手机端请求超时） |
| AstroBox pluginsystem | 已批准的 CanopusConnect 权限在 30 秒内不再问前端（只缓存“批准”，拒绝每次重问） |
| Canopus Supervisor `canopus_supervisor_l2.c` | 拥有者线程一次最多处理 4 个排队请求；应答队列满时请求留在队里，不再丢掉它的应答 |
| 手表端 `import.rs` | 比期待偏移稍早到的帧（最多 4 帧、不超过 4×464 字节）先收着，等前面的到齐再依次写入，不再立刻要求手机回退 |
| `lyra-transfer` | 确认偏移超过游标时（回退之后的迟到确认）把游标推到确认处，不再下溢；窗口计算用饱和减法 |

Mirage `.043`，同一组文件（MP3 401,283 B、封面 123,916 B、LRC 391 B，合计 525,590 B、1,139 帧），
每个数字是同一台设备上的一次完整导入，导入后关机回读，三个文件逐字节一致、曲库里只有一条：

| 在途帧数 | 耗时 | 速度 | 重传 |
|---|---|---|---|
| 1（旧行为） | 36.1 s | 14.2 KiB/s | 0 |
| 3 | 14.8 s（两次） | 34.7–34.8 KiB/s | 0 |

约 2.4 倍。这是模拟器：它的链路延迟与真机不同。真机上一次往返通常更长，在途帧数的收益预计更大，但没有测过，不能由此推出真机的速度。
旧的“一次一帧”路径仍然存在（`--pipeline 1`），主机没升级时手表端照常工作。

**没有做的**：接近系统里 L2 传 Mass 的速度需要框架侧的连续数据通道（发送端不逐条等应答、手表端有带信用的接收环）。
这一轮只是把“每个往返一帧”改成“每个往返三帧”。Supervisor 的静态内存已经贴着上限（`.043` 常驻 162,634 / 163,840 字节），
接收环要放进堆里按需分配，不能放进常驻段。

早先几处文档里的“11.7 KiB/s 已是链路下限”的说法已经撤回：它测的是旧的逐条等待响应的路径。

## 播放：卡顿、进度落后与起播慢（2026-10-24）

真机（Band 10 Pro）报告：界面一动、歌词每次带动画切换都会卡；界面进度比耳机里慢约 20 秒，歌词同样；起播慢约 3 秒。
下面的原因来自代码与固件反汇编，修复只在主机测试和 Mirage（无蓝牙 sink，`dry-run`）里验证过，**真机未验证**。

### 进度慢约 8 %（不是卡顿造成的）

BluetoothAudio 模块把 48 kHz（以及 24 kHz）的 MP3 重采样到 44.1 kHz，`pcm_frames` 数的是重采样后的 44.1 kHz 帧，
`decoded_sample_rate` 报的却是 MP3 自己的 48 kHz。Lyra 用 `pcm_frames / decoded_sample_rate` 算位置，于是时钟慢
44.1/48 = 0.919：4 分钟的歌到结尾差 19.5 s。结束时机由驱动的 STOPPED 决定，所以“结束恰到好处”。卡顿只会让耳机和
`pcm_frames` 一起停，造不出这种差距。44.1 kHz 的文件不受影响。

修复在模块：`StreamProgress::Frame` 带上 `source_frames`，`pcm_frames` 改数 MP3 自己采样率下的帧；头文件与
`THIRD_PARTY_PLAYBACK.md` 写明 `pcm_frames / decoded_sample_rate` 就是播放位置。**需要同时更新 BluetoothAudio 模块。**

### 起播慢：ID3 标签

插件原样上传 MP3，内嵌封面的 ID3v2 标签常有几百 KB 到 1 MB 以上。模块解码器要先把标签读过去，而 Lyra 每 50 ms
只能往 16 KiB 的输入环里塞一次：1 MB 标签约 3 s 静音。现在：

* 插件上传前去掉开头的 ID3v2 与结尾的 APEv2、ID3v1（`id3::audio_range`），只传音频帧，传输量同时变小；
* 手表打开文件时跳过开头的 ID3v2 标签（能 `lseek` 就跳，不能就在读取线程里读过去），已经导入的旧歌也受益。

### 卡顿

固件事实（036 反汇编）：模块的包定时器和 Lyra 的音频 tick 都在 `bluelet_thread`（优先级 103）上跑；
UI 主任务 `miwear` 是 102，`fb_flush_thread` 是调用者 +1 = 103。也就是说 UI 渲染本身抢不走蓝牙线程，
界面变化造成卡顿只能经由共享资源（闪存/文件系统、内存带宽：固件用 VGLite GPU 渲染）或同优先级的刷屏线程。
原实现在这两点上都很脆弱：

1. **蓝牙线程做阻塞的文件读取**：Lyra 每 50 ms 在 `bluelet_thread` 上 `read` 最多 8×4 KB 的 MP3。界面读封面、
   图标、字体或导入写文件时，这次读就要等，而同一线程上的 A2DP 包定时器也跟着停。
2. **包节奏丢掉的时间不补**：模块每次回调只发一个包，回调迟到超过 50 ms 就把截止时间重置到“现在”。
   一次停顿让耳机的缓冲（启动时只预填约 150 ms 静音）永久少一截，之后任何小停顿都会被听到。

修复：

* 模块 `PacketClock`：按一个固定锚点计算应发的包数，迟到的包一次回调最多补发 3 个（流控窗口仍是 2 个在途），
  落后超过 400 ms（耳机肯定已经断流）才重定锚点；锚点在第一个音频包发出时才建立，跳标签、等输入的时间不算欠账。
  暂停后恢复重定锚点。模块“耳机”详情页的 Underruns 行会显示本次播放最大落后 `late N ms`，真机上用来判断
  蓝牙线程实际被卡了多久。
* Lyra `feeder`：MP3 改由 Supervisor 的后台定时器（UI owner 线程，每 10 ms，熄屏也跑）读进 32 KiB 的块环，
  蓝牙线程只从内存拷贝。每块带请求的 epoch，切歌只换 epoch。Supervisor 没有后台定时器时（旧版 Supervisor 的 036、139）
  照旧在蓝牙线程读；新版 Supervisor 在五个目标上都有（见下面“036、139 的后台定时器”）。读取线程超过 1 s 没有供数时，蓝牙线程按已消耗的字节数 `lseek` 到同一位置自己接着读。

Mirage `.043`（`dry-run`）：读取器运行、发布了 118 块（约 470 KB），自动切歌、歌词、导入回归（两次导入后关机回读，
三个文件逐字节一致）都正常。模拟器没有蓝牙 sink，包节奏的改动只有主机测试（`tests/media.rs`）覆盖。

### 继续降低 UI 刷新时的偶发卡顿（2026-10-24）

用户在 10 Pro `.043` 实机上反馈：此前优化有效，但 UI 操作、歌词切换仍概率性卡顿，熄屏大概率正常。
本轮保留读盘线程分离与歌词动画，继续改两处：

* BluetoothAudio 的音乐节奏器保持 **80 ms 提前量**（加上至多一个 SBC 包的取整），不再只在已经迟到后补包。
  起播静音不等于运行期间一直有音乐缓冲；让真实音乐小幅提前发送，为短时 owner 调度延迟留余地。仍遵守已有流控
  窗口与每次最多 3 包的工作预算，不扩大输入环，不把整首歌提前交给耳机。暂停恢复保留该目标，超过 400 ms 的严重
  断流仍重定锚点；`late` 仍报告落后真实时间的部分，而不是未填满提前量的部分。
* Lyra 的曲库刷新 key 只读 transport 枚举，不再为一个状态值生成整份 `PlayerView`；上一首/下一首可用性查询借用
  歌曲而不复制元数据；播放页 diff 移动旧/新快照，不再每 100 ms 额外复制两份标题、作者、封面路径等字符串。

### 导入写入

手表收到的每帧 464 字节原来直接写一次文件；现在攒满 4 KiB 整块再写（`ASSET_END` 时写剩余部分并 `sync`），
处理函数在 UI owner 上占用的时间和手机等应答的时间都更短。插件的进度行新增“往返 N ms”：每帧从交给宿主到
手表收下的平均时间。3 帧在途时速度约等于 3×464 B / 往返时间，真机上用它判断瓶颈是不是链路往返。

### 深接收环（2026-10-24）

3 帧在途时速度 ≈ 3×464 B / 往返时间；真机往返约 140 ms 就正好是 10 KiB/s。瓶颈在 Supervisor 只有 4 槽的
L2 接收环（手机最多 3 条在途），所以改了框架（细节见 Canopus `ADR-CAN-009` “在途窗口”）：

* Supervisor：接收环 16 槽，放在堆上；QUERY_DEVICE +84 报告环深；应答与事件轮流发，PROGRESS 不再被应答饿死；
* AstroBox core：插件 `listen` / 重连 `resync` 时问一次环深，插件窗口放宽到环深减一；旧 Supervisor 不报告，保持 3；
* 插件：`IN_FLIGHT` 3 → 15，实际在途数由宿主按手表环深决定。

Mirage `.043`，525,590 字节、1,139 帧，导入后关机逐字节回读一致：

| 在途帧数 | 耗时 | 速度 |
|---|---|---|
| 1 | 37.6 s | 13.6 KiB/s |
| 3 | 10.1 s | 50.7 KiB/s |
| 15 | 6.6 s | 77.6 KiB/s |

（3 帧比此前的 34.7 KiB/s 快，是手表端改成 4 KiB 整块写入之后。）同一个 AstroBox 对旧 Supervisor 的设备让 15 帧在途时，
窗口仍是 3，约 35 KiB/s，无超时、无重传。若真机往返仍约 140 ms，15 帧在途的上限约 50 KiB/s；实际以插件显示的往返为准。
需要同时更新 Supervisor（重新运行安装表盘）和 AstroBox。

### 静默丢回包的发送失败路径（2026-10-24）

用户报告：新 Supervisor 下导入停在 0 KB/s、曲库无响应，模块安装可用；较旧的 ABI 2.0 Supervisor 正常，
最后可用版本猜测为 `d3c4678`，未确认。当前主线 Supervisor 与新编译的 Lyra 在 Mirage `.043` 上原样 HELLO、
LIST、两次 525,590 字节导入及关机逐文件回读均通过（约 83 KiB/s），所以尚未复现实机回归，不能把它说成 ABI 不匹配。

代码检查找到独立的确定缺陷：`l2_drain` 忽略原生发送返回值，分配失败/背压时仍释放回包；模块已收到请求，
手机却永远等不到该回复。Canopus 现保留失败的响应/事件并在后续 BT tick 重试。原生 send 会原地加密，故使用工作副本，
队列保留明文，避免重试时再次加密密文。ARM 回归注入“修改载荷后发送失败”，旧代码确定丢帧，修改后保持原文与顺序；
断连后的旧会话帧仍丢弃。补丁后 Mirage `.043` 再做两次 525,590 字节导入：6.6 s，77.5 / 78.0 KiB/s，
无恢复重传；关机回读音频、封面、歌词逐字节一致，重启后的 HELLO / LIST、播放页暂停/切歌及歌词浏览回归通过。
此处用真实 AstroBox core 和共享发送器，不是完整 WASM 插件宿主，也没有蓝牙耳机 sink。该发送失败缺陷已修复，
但它是否就是用户实机回归的完整根因仍需真机复测。

### 036、139 的后台定时器（2026-10-24）

后台定时器（熄屏也触发）原来挂在 Supervisor 的 L2 后端上，而 036、139 没有恢复出 L2 所需的 SAR/会话/加密入口，
所以这两个固件上 `timer_set_background` 一直不支持，`feeder` 只能退回蓝牙线程读。其实后台定时器只需要 UI 所属的
libuv 循环和 `uv_timer_init` / `uv_timer_start`：Canopus 把这部分拆成独立的 owner 泵，并从固件里找到了这两个目标的
地址（036：循环 `0x20121F80`、init `0x0C2CD84C`、start `0x0C2CDA3C`；139 与 155 相同），见 Canopus
`evidence/owner-pump.json`。Mirage 里在 036、139 的原版固件上读 libuv 定时器堆：Supervisor 的常驻定时器每 10 ms 到期一次，
熄屏期间到期时间随循环时间前进。装新版 Supervisor 后，Lyra 在这两个固件上也走 UI 线程读取。
（139 的固化启动仍不支持：它在 Mirage 里没跑通，与后台定时器无关，所以没有一起打开。）
